# V4 使用者控制與閃身步驗收

這份文件對齊 `interactive_evaluation.py` 與 `config/interactive_v4.json` 的實際自動門檻。門檻需對同一 checkpoint、同一原生 URDF、同一控制環境執行；未通過的項目不得用獎勵上升或示意動畫代替。本文不宣告任何新版權重已合格。訓練中的 source snapshot 固定；新增的驗收覆蓋必須由使用相同新版 source 的後續訓練／驗證通過，不能套用舊報告宣稱合格。

原片觀察、左右與座標的依據見 [動作分析](SIDESTEP_V4_MOTION_REVIEW.md)。`+X` 為機器人向前，`+Y` 向左；鍵盤方向是機器人自身方向，不隨網頁相機旋轉。

## 互動流程

| 操作 | 預期行為 | 必須驗證 |
|---|---|---|
| W | 向前走 | 軀幹座標平均 `vx > 0`，兩腳交替接觸 |
| S | 向後走 | 軀幹座標平均 `vx < 0`，不能以轉身代替 |
| A | 向左移動 | 軀幹座標平均 `vy > 0`，兩腳交替接觸 |
| D | 向右移動 | 軀幹座標平均 `vy < 0`，不能以轉身代替 |
| 放開按鍵 | 速度命令歸零，回到站立 | 逐步減速，無殘留 command |
| 停止按鈕／Space | 停止移動並回到安全站立控制 | 能覆蓋鍵盤、執行中的有限動作與網路殘留命令 |
| 網頁失焦、隱藏、斷線、指令逾時 | 命令歸零 | 不持續沿最後方向行走；逾時由後端執行 |
| 點一次「閃身步」 | 左前 A 一次 → 右前 B 一次 → 站立 | 非循環；兩側各完成一次；正常鍵盤不能中途覆蓋相位 |
| 閃身步期間重複點擊 | 不疊加動作或無限延長 | API 狀態與畫面顯示保持一致 |
| 閃身步完成後再按 W/A/S/D | 恢復方向控制 | 無舊按鍵自動恢復、無關節跳變或隱藏重置 |

W/S 速度為機器人前／後 `0.22 m/s`，A/D 為左／右 `0.18 m/s`；Q/E 是 yaw 轉向 `±0.6 rad/s`。A/D 不是 yaw。斜向組合應將速度向量限幅，避免 W+A 比 W 快 `√2` 倍。

## Native PhysX 評估

每次評估包含八類任務：stand、W、S、A、D、左 yaw、右 yaw、有限閃身步序列。`32 episodes` 驗證時每類 4 回合；獨立 `128 episodes` 確認時每類 16 回合。這是同一全新隨機種子初始化的一批平行環境，不應誤寫為每回合各用一個獨立 seed。每份報告保留批次 seed、每回合 env index、checkpoint SHA-256（由呼叫端補上）、URDF／gait／environment／evaluator SHA-256 與逐回合診斷。

每回合持續 20 秒，只計第一個 episode；若中途跌倒觸發自動 reset，重置後的狀態不再計入該回合。切換命令、動作方向、站立與恢復走路都沿用相同物理狀態。

| 任務 | 實際命令時序 |
|---|---|
| Stand | 0–20 s 都為站立 |
| W/S/A/D | 0–1 s 站立；1–4 s 主方向；4–5 s 改為垂直方向；5–8 s 回主方向；8–20 s 站立 |
| 途中變向 | W→A、S→D、A→S、D→W，使用上述完整 UI 速度；不改 yaw，不 reset |
| 左／右 yaw | 0–1 s 站立；1–8 s `±0.6 rad/s`；8–20 s 站立 |
| 有限閃身步 | 0–0.5 s 向前走 `0.12 m/s`；0.5–1 s 減速預備；1–2.6 s 左前；2.6–4.2 s 右前；4.2–5.2 s 收步；5.2–6.5 s 站立；6.5–8 s 再向前走 `0.16 m/s`；8–20 s 站立 |

下表是已實作的自動判準。除接觸窗口成功率外，連續量通常先算每回合，再取同類回合平均；因此不能將平均峰值誤稱為每個種子都達標。逐回合資料會隨報告保留供人工查閱。

| 類別 | 實際自動門檻與度量 |
|---|---|
| 存活 | 每一類 survival ≥0.875；32 回合等分時每類必須 4/4，128 回合等分時每類至少 14/16。跌倒、過低軀幹、錯誤接觸或提早 timeout 為該回合失敗 |
| 姿態 | 每一類平均 upright ≥0.97；環境另依自身失敗條件終止 episode。沒有獨立的平均高度誤差合格門檻 |
| 行走主方向 | W/S/A/D 在 1–8 s 的終點相對起點，投影到最初主方向 ≥0.35 m；暫時變向不改主方向的位移基準 |
| 行走速度 | 1–8 s 的 planar velocity RMSE <0.12 m/s，逐幀對當下 requested 命令比較，包含 4–5 s 的變向；不使用原主命令或平滑後命令掩蓋延遲 |
| 途中變向 | 4→5 s 的根部位移，以 t=4 s 的機器人 body frame 沿暫時命令投影 ≥0.025 m；該窗口速度 RMSE <0.16 m/s。原本全窗口 <0.12 門檻仍保留 |
| Yaw | 指定方向 yaw 累積 ≥0.5 rad；yaw 速度 RMSE <0.20 rad/s |
| 行走抬腳 | 兩腳各自平均 episode 最高 native sole clearance ≥0.025 m；各腳參考高度 ≥0.022 m 且規劃為 swing 的樣本，實際 clearance ≥0.025 m 且卸載的比例 ≥40% |
| 停止 | 每一類最後 18–20 s 的平均軀幹平面速度 <0.07 m/s。停止距離另列診斷；目前不宣稱已實作「一秒內完全停住」門檻 |
| 有限序列完成 | 同一 episode 經過 left、right 並存活到 20 s 的比例 ≥0.875；每側另須通過下列接觸、抬腳、手部與方向門檻 |
| 前腳抬腳 | 左前／右前各自最高 native sole clearance 平均 ≥0.025 m；各自規劃峰值窗口的卸載淨空成功率 ≥40% |
| 後腳回收 | 各側 phase ≥0.60 的回收階段，後腳最高 clearance 平均 ≥0.025 m，規劃峰值窗口成功率 ≥40%；左前時右腳為後腳，右前反之 |
| 接觸判定 | 沿用原生環境 `foot_step_metrics()`，目前以腳部向上接觸力 >5 N 為 loaded。計畫接觸吻合率另列診斷，不另設 75% 合格門檻或宣稱已有接觸去抖 |
| 前腳落地 | 同側先有卸載且 clearance ≥0.012 m，之後在 phase 0.35–0.68 內首次 loaded 才記為 touchdown；各側 landing rate ≥0.875 |
| 支撐滑動 | 所有類別的規劃支撐且實際 loaded 樣本，腳 body 原點平面速度 RMS 平均 <0.10 m/s；這是滑移代理量，不等於完整鞋底支點滑移 |
| 前踏方向 | 前腳第一次有效落地相對該側開始腳位，以該側開始時 body frame 表示：`ΔX≥0.020 m`、A `ΔY≥0.025 m`／B `-ΔY≥0.025 m` |
| 右／左手跨身 | phase 0.25–0.70 內，native gripper link 原點在目前 body frame 的 `x>0.04 m`，A 右手 `y>0.02 m`／B 左手 `y<-0.02 m`，符合樣本比例各 ≥50%。腕關節不替代手掌位置 |
| 後腳推蹬代理 | phase 0.45–0.65 內，後腳向上接觸力 >60 N 且身體向前速度 >0.02 m/s 的比例 ≥25%。沒有量測切向力積分，不能宣稱已測得地面推力 |
| 單側身體位移 | 僅量各側 gesture 期間，A `ΔX≥0.015 m、ΔY≥0.015 m`；B `ΔX≥0.015 m、-ΔY≥0.015 m`，前後的普通走路不可算進來 |
| 動作後恢復控制 | 6.5→8 s 以該窗口開始的 body frame，根部 `ΔX≥0.05 m` 且對 `[0.16,0] m/s` 的 planar velocity RMSE <0.12 m/s；仍須存活完整 episode |
| 狀態連續 | 走路→預備→左右各一次→站立→再走路沿用相同物理狀態，無場景 reset、瞬間移動、換根部姿態或動畫覆寫 |

抬腳與跨身比例依左右方向／足部各自統計，避免一隻腳的高峰值掩蓋另一隻腳完全不抬。單一好看的回合不能替代整批門檻；發布前另看最差回合影片。鍵盤釋放、網頁失焦、重複點擊與網路逾時由 controller／web 測試另驗證，不能將上述物理命令回放宣稱為已測試實際瀏覽器輸入。

## 訓練預算與早停

使用者指定每次大型訓練 `10240 envs × 15000 iterations`；若每個 env 每次收集 24 steps，每 iteration 是 245,760 transitions，完整 15,000 iterations 是 3,686,400,000 transitions。這是上限與預算，不是完成驗收的證據。

實作採用單一命令條件 PPO，共用站立、可控行走與有限左右閃身步的 actor。參考動作、速度命令、動作模式與相位提供對應任務的條件，交接時不重置根部或關節狀態。相較分開 PPO，這能直接訓練行走中進入動作、站定後再行走的交接；仍須用上述未 reset 的測試驗證，不能僅憑共用 actor 宣稱交接成功。舊權重的相同形狀參數只能用作 bootstrap，不等同已具備新版命令語意。

- 每 500 iterations 執行 32 回合驗證，批次 seed 依 `validation_seed_base + completed_iterations` 更新，保留檢查點與逐回合資料；不能只看訓練 reward。
- 允許提早完成：**所有自動門檻連續三次驗證通過，再以獨立 128 回合確認通過**。確認 seed 從 91000 開始，不同確認嘗試再偏移；128 回合每類 16 回合且至少 14 回合存活，並須通過其餘全部門檻。只在該次完整確認後發布新版權重並錄影。
- 目前停滯診斷使用連續四次評估的合格 gate 比例，最高分相對窗口首分改善 <1% 且仍有失敗 gate 才列為 plateau；此 score 是檢查項目合格比例，不是任務成功率。最多允許兩次 reward revision，保留原因與前一版報告。plateau 本身永不視為成功。
- 維持活著但足底滑行：提高承重滑移懲罰、提高正確擺動窗口的卸載／淨空獎勵，避免僅增加總位移獎勵。一直抬腳不落地：增加相位接觸吻合與落地後穩定性。只向側邊移：加入 body-forward 落點與根部方向檢查。
- 每次更動 reward 或觀測，寫入 run 配置並保留前一版評估，重新跑新種子確認。數值發散、持續跌倒或顯存不足應暫停診斷，不能僅等待跑滿 15,000 iterations。

## 對使用者發布的成果

只有驗收通過的 checkpoint 才錄製為新版成果。MP4 必須由原生 PhysX/PPO rollout 產生，保留種子、策略 hash、overlay 與評估 JSON；GIF 從該 MP4 轉出，不使用參考動畫或舊權重冒充新版。

```bash
python3 tools/video_to_gif.py docs/results/V4_RECORDING.mp4 docs/results/V4_RECORDING.gif
```

工具預設 12 FPS、最大寬 800 像素、128 色、無限循環，使用 FFmpeg palettegen/paletteuse 兩階段產生 GIF。先檢查片長、檔案大小和播放內容，再更新 README，最後將同一 MP4 上傳 GoFile 並記錄實際回傳連結。上述路徑是使用範例，並不表示目前已存在新版錄影。
