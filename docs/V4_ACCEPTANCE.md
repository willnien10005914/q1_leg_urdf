# V4 使用者控制與閃身步驗收

這份文件定義新版應達到的行為與建議評估門檻。門檻需對同一 checkpoint、同一原生 URDF、同一控制環境執行；未通過的項目不得用獎勵上升或示意動畫代替。本文不宣告任何新版權重已合格。

原片觀察、左右與座標的依據見 [動作分析](SIDESTEP_V4_MOTION_REVIEW.md)。`+X` 為機器人向前，`+Y` 向左；鍵盤方向是機器人自身方向，不隨網頁相機旋轉。

## 互動流程

| 操作 | 預期行為 | 必須驗證 |
|---|---|---|
| W | 向前走 | 軀幹座標平均 `vx > 0`，兩腳交替接觸 |
| S | 向後走 | 軀幹座標平均 `vx < 0`，不能以轉身代替 |
| A | 向左移動 | 軀幹座標平均 `vy > 0`，兩腳交替接觸 |
| D | 向右移動 | 軀幹座標平均 `vy < 0`，不能以轉身代替 |
| 放開按鍵 | 速度命令歸零，回到站立 | 逐步減速，無殘留 command |
| 停止按鈕／Space | 停止移動並回到安全站立控制 | 能覆蓋鍵盤、執行中的有限動作與網路殘留命令 |
| 網頁失焦、隱藏、斷線、指令逾時 | 命令歸零 | 不持續沿最後方向行走；逾時由後端執行 |
| 點一次「閃身步」 | 左前 A 一次 → 右前 B 一次 → 站立 | 非循環；兩側各完成一次；正常鍵盤不能中途覆蓋相位 |
| 閃身步期間重複點擊 | 不疊加動作或無限延長 | API 狀態與畫面顯示保持一致 |
| 閃身步完成後再按 W/A/S/D | 恢復方向控制 | 無舊按鍵自動恢復、無關節跳變或隱藏重置 |

WASD 建議先驗證純平移，再視設計加入 Q/E 轉向；若 UI 選用 A/D 轉向，則必須明確更改標示及本表，不能將方向控制和側移的驗收混用。斜向組合應將速度向量限幅，避免 W+A 比 W 快 `√2` 倍。

## Native PhysX 評估

先以固定場景檢查，再使用至少 32 個全新種子確認。方向命令每段持續 3–5 秒，涵蓋前、後、左、右、停止及閃身步交接；固定初始姿態的單一成功回合只能作預覽。每個評估檔必須保留 checkpoint SHA-256、URDF SHA-256、seed、episode 長度、各項指標與成功數。

以下為預設建議門檻，應在開訓前固定並隨實際配置版本化；調整時須記錄原因。

| 類別 | 建議門檻與度量 |
|---|---|
| 存活 | 新種子 32 回合至少 31 回合完成；跌倒、過低軀幹或錯誤接觸明確計為失敗 |
| 姿態 | 完成回合平均 upright ≥0.94；高度誤差 ≤0.07 m，並檢查最低瞬時值避免平均掩蓋跌落 |
| 行走方向 | 每一方向的命令投影速度為正；暖機後速度 RMSE ≤0.12 m/s，3 秒沿命令位移 ≥0.20 m；反向／橫向誤差單獨記錄 |
| 行走抬腳 | 左右腳都出現交替卸載與擺動；不能靠兩腳持續接地滑行達到位移 |
| 停止 | 命令歸零後 1 秒內，軀幹平面速度降至 ≤0.08 m/s，維持雙足穩定至少 1 秒 |
| 左右完整性 | 每次按鈕事件 A/B 完成計數各為 1，最後進入 stand；任何一側缺失均失敗 |
| 前腳抬腳 | 各側在其規劃擺動窗口，native sole 最低點達 ≥0.025 m 且腳已卸載；峰值目標 0.03–0.04 m，不能只有 toe/body 原點升高 |
| 後腳回收 | 各側推蹬完成後再出現 ≥0.025 m 的卸載回收，目標峰值窗口成功率 ≥40%；不可將仍然承重的腳抬高當作合格 |
| 接觸時序 | 支撐／擺動計畫吻合率 ≥75%；擺動中至少連續 0.06 s 不承重，前腳有效接觸後才卸載後腳 |
| 接觸判定 | 有力感測時使用正向力與時間去抖，例如 `Fn≥15 N` 維持 0.04 s 表示支撐、`Fn<10 N` 表示卸載；閾值需對 42.2 kg native CAD 檢查，不套用到不同機器人 |
| 支撐滑動 | 承重腳平面速度 RMS ≤0.10 m/s；若以 body 原點速度近似，另檢查 foot rotation 與支點變化；記錄累積滑移量 |
| 前踏方向 | A 左腳落點相對該腳起點有正向 `ΔX` 與正向 `ΔY`；B 右腳正向 `ΔX` 與負向 `ΔY`；初始最低方向檢查為前進 ≥0.03 m、側移 ≥0.04 m |
| 右／左手跨身 | A 右手跨到軀幹中線左側、B 左手跨到右側，且在軀幹前方；以 native gripper link 原點的 body-frame 位置量測，跨身時間需與前腳擺動／落地重疊。腕關節位於手掌後方，不作為手掌位置的替代 |
| 後腳推蹬 | A 右腳、B 左腳在承重窗口有正的指定方向地面力積分；同一窗口身體在指定前側方向移動。若未配置切向力感測，只能報位移＋支撐的代理指標，不能宣稱已量得推力 |
| 單側身體位移 | A `ΔX>0`、`ΔY>0`；B `ΔX>0`、`ΔY<0`，建議各側指定方向投影 ≥0.03 m；只擺腿但身體不前進不合格 |
| 左右後站定 | 完成後速度 ≤0.08 m/s、雙足站立至少 1 秒；初始航向誤差 ≤10°。左右可抵消側移，但不要求抵消前進量 |
| 接續控制 | 同一物理狀態完成 walk→sidestep→stand→walk，無場景 reset、瞬間移動、換根部姿態或動畫覆寫物理狀態 |

閃身步各項比例應以「每側、每個事件」先判定，再計算成功率，避免一隻腳的高峰值掩蓋另一隻腳完全不抬。建議至少 90% 有效事件完成兩側抬腳、跨身與方向檢查，並保留最差種子供人工看影片。

## 訓練預算與早停

使用者指定每次大型訓練 `10240 envs × 15000 iterations`；若每個 env 每次收集 24 steps，每 iteration 是 245,760 transitions，完整 15,000 iterations 是 3,686,400,000 transitions。這是上限與預算，不是完成驗收的證據。

推薦將可控行走與有限閃身步分開學習、共用原生機器人控制介面與安全站立；在同一物理狀態交接時，前一個策略最後動作、關節位置／速度與軀幹姿態都不可被重置。若轉成單一命令條件 PPO，觀測必須顯式含速度命令、動作類別、左右方向與有限動作相位；重訓與播放必須使用一致的契約，舊權重不能直接套上新增維度。

- 每 500 iterations 以固定 validation 種子評估，保留各個檢查點；最佳模型依可控性、完整雙側接觸與存活選擇，不能只看訓練 reward。
- 允許提早完成：完整驗收連續三次達標，再以未用過的 32 個種子確認通過；錄製一般種子及最差通過種子，交給使用者看動作。
- 若連續四個檢查點的方向追蹤、雙側抬腳成功率或最差側成功率幾乎不改善，並且尚未達門檻，列為停滯。先查幾何、接觸感測、參考可達性與各 reward 分量，再調整 reward／課程；不能將停滯當作已學會。
- 維持活著但足底滑行：提高承重滑移懲罰、提高正確擺動窗口的卸載／淨空獎勵，避免僅增加總位移獎勵。一直抬腳不落地：增加相位接觸吻合與落地後穩定性。只向側邊移：加入 body-forward 落點與根部方向檢查。
- 每次更動 reward 或觀測，寫入 run 配置並保留前一版評估，重新跑新種子確認。數值發散、持續跌倒或顯存不足應暫停診斷，不能僅等待跑滿 15,000 iterations。

## 對使用者發布的成果

只有驗收通過的 checkpoint 才錄製為新版成果。MP4 必須由原生 PhysX/PPO rollout 產生，保留種子、策略 hash、overlay 與評估 JSON；GIF 從該 MP4 轉出，不使用參考動畫或舊權重冒充新版。

```bash
python3 tools/video_to_gif.py docs/results/V4_RECORDING.mp4 docs/results/V4_RECORDING.gif
```

工具預設 12 FPS、最大寬 800 像素、128 色、無限循環，使用 FFmpeg palettegen/paletteuse 兩階段產生 GIF。先檢查片長、檔案大小和播放內容，再更新 README，最後將同一 MP4 上傳 GoFile 並記錄實際回傳連結。上述路徑是使用範例，並不表示目前已存在新版錄影。
